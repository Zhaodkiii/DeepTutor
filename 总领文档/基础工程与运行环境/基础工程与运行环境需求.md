# 基础工程与运行环境需求

## 一、模块目标

本模块负责 DeepTutor 的启动、配置、运行根目录、日志、进程编排和全局生命周期。它决定“项目如何跑起来”，也决定后续所有服务读取哪一套设置、写到哪一套目录。

## 二、基础工程与运行环境模块结构

### 2.1 启动入口与进程编排

#### 需求说明

项目需要同时支持：

- `deeptutor start` 一键拉起后端和前端。
- `deeptutor serve` 只启动 API 服务。
- 生产/容器/本地开发时都能读取一致的运行根目录。

#### 基础要求与业务规则

- CLI 与 API 共享同一套运行时模式。
- 启动器必须清楚区分前后端进程，支持优雅退出。
- Windows 需要特殊处理子进程和事件循环。

#### 验收标准

- 可以通过 `deeptutor_cli/main.py` 启动 Web 服务。
- `deeptutor/api/run_server.py` 能独立启动 FastAPI。
- 停止命令能回收前后端子进程。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| CLI 总入口 | `deeptutor_cli/main.py` |
| 本地 Web 启动器 | `deeptutor/runtime/launcher.py` |
| API 启动脚本 | `deeptutor/api/run_server.py` |
| 运行模式 | `deeptutor/runtime/mode.py` |

### 2.2 配置、路径与运行根目录

#### 需求说明

系统需要把 workspace root、data root、settings、runtime cache 和生成物目录稳定地绑定到同一套路径规则上。

#### 基础要求与业务规则

- 优先使用显式 `home`，其次是 `DEEPTUTOR_HOME`，最后回退到当前工作目录。
- 用户级设置必须与 workspace 绑定，而不是写死在代码目录。
- 启动前要把运行时设置导出到环境变量。

#### 验收标准

- 不同启动方式下，`data/user/settings/` 与 `data/knowledge_bases/` 的定位一致。
- 环境变量覆盖与文件配置读取顺序可预测。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| 运行根目录解析 | `deeptutor/runtime/home.py` |
| 配置装载与路径解析 | `deeptutor/services/config/__init__.py`、`deeptutor/services/config/loader.py` |
| 默认配置与常量 | `deeptutor/config/defaults.py`、`deeptutor/config/constants.py` |

### 2.3 日志、健康与全局生命周期

#### 需求说明

启动时需要完成日志配置、工具一致性校验、LLM 初始化、事件总线、伙伴自动启动、cron 启动、PocketBase 检查和记忆迁移。

#### 基础要求与业务规则

- 关键失败应记录警告或错误，但不应让整个应用在非致命问题上直接崩溃。
- WebSocket 噪声和敏感 token 需要在日志里做过滤或脱敏。

#### 验收标准

- 应用启动时能完成全局初始化。
- 冲突配置能在启动阶段被发现。
- 不会因为普通 WebSocket 断连把日志刷爆。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| FastAPI 生命周期 | `deeptutor/api/main.py` |
| 日志配置 | `deeptutor/logging/*` |
| 事件总线 | `deeptutor/events/event_bus.py` |
| cron 服务 | `deeptutor/services/cron/service.py` |
| 记忆迁移 | `deeptutor/services/memory/*` |

## 三、基础工程与运行环境模块功能

### 3.1 启动与停止

#### 需求说明

提供面向开发和运行的统一启动/停止接口。

#### 基础要求与业务规则

- `start` 会同时处理后端和前端。
- `serve` 只负责 API。
- `restart` 必须先停再起。

#### 验收标准

- 端口占用正确处理。
- 子进程退出时不会遗留孤儿进程。

#### 技术细节与设计代码位置

- `deeptutor_cli/main.py`
- `deeptutor/runtime/launcher.py`
- `deeptutor/api/run_server.py`

### 3.2 配置与环境导出

#### 需求说明

运行时配置需要从文件和环境变量统一解析，再注入到启动后的服务里。

#### 基础要求与业务规则

- `ensure_runtime_settings_files()` 必须先于服务装配。
- `export_runtime_settings_to_env()` 负责把文件配置变成进程内可读的环境信息。

#### 验收标准

- LLM、RAG、Auth、UI 相关设置都能在同一进程中读取到。

#### 技术细节与设计代码位置

- `deeptutor/services/config/__init__.py`
- `deeptutor/services/config/runtime_settings.py`
- `deeptutor/services/config/loader.py`

### 3.3 全局生命周期与守护任务

#### 需求说明

应用启动后需要串联 EventBus、伙伴、cron 和外部存储检查。

#### 基础要求与业务规则

- 这些任务属于运行态守护，不应该嵌入单次 turn 的业务逻辑。
- 失败应尽量降级，避免影响主业务。

#### 验收标准

- 守护任务能在启动和停止时正确进入/退出。

#### 技术细节与设计代码位置

- `deeptutor/api/main.py`
- `deeptutor/services/cron/service.py`
- `deeptutor/services/partners/*`
- `deeptutor/events/event_bus.py`

## 整体业务流程

```text
启动命令
  ↓
读取运行根目录和配置
  ↓
导出环境变量并配置日志
  ↓
校验工具/能力一致性
  ↓
初始化 LLM、事件总线、伙伴、cron
  ↓
检查外部依赖与迁移历史数据
  ↓
进入服务监听状态
```

## 状态模型

- 进程态：CLI 进程、API 进程、前端进程。
- 运行态：启动中、已就绪、停止中、异常退出。
- 配置态：文件配置、环境变量、运行时导出值。
- 路径态：workspace root、data root、cache root、输出目录。

## 数据与持久化

本模块不直接保存业务数据，但负责定义所有业务模块的数据落点和运行根目录。

## 错误模型

- 配置缺失：启动时回退到默认值或报错退出。
- 端口冲突：启动器应提示并停止。
- 外部依赖不可达：记录警告，但尽量不阻塞核心服务。
- Windows 事件循环或编码问题：使用专门兼容逻辑。

## 与其他模块的接口边界

- 向下：负责提供运行时根目录、环境变量、日志和生命周期。
- 向上：被 CLI、API、前端启动器和所有服务层使用。
- 不负责：具体对话、知识库、Book、学习或伙伴业务规则。

## 测试策略

- 启动与停止流程需要集成测试。
- 路径解析与环境变量覆盖需要单元测试。
- Windows 兼容分支需要至少保留一组回归测试。

## 当前实现、缺口与演进

当前实现已经具备完整启动链路，但配置分散在文件、环境变量和 runtime service 中，长期建议继续收敛命名和入口。

## 整体验收标准

- [ ] 能从 CLI 和 API 两种入口启动。
- [ ] 运行根目录一致。
- [ ] 日志、生命周期和守护任务正常工作。
- [ ] 外部依赖失败时有明确降级或报错。
