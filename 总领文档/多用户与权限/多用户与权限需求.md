# 多用户与权限需求

## 一、模块目标

本模块负责 DeepTutor 的登录、登出、注册、角色、资源授权、个人资料、移动端 token 和 admin 分配。它把“谁可以看到什么、可以用什么、可以写到哪里”变成明确约束。

## 二、多用户与权限模块结构

### 2.1 认证与会话身份

#### 需求说明

系统需要支持网页登录、会话 token、cookie、Bearer header 和 WebSocket 身份验证。

#### 基础要求与业务规则

- HTTP 和 WebSocket 的身份判断要一致。
- SameSite / Secure 策略要适配本地开发和远程访问。

#### 验收标准

- 登录后能访问受保护接口。
- WebSocket 能正确鉴权。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| auth router | `deeptutor/api/routers/auth.py` |
| 认证服务 | `deeptutor/services/auth.py` |
| 身份上下文 | `deeptutor/multi_user/context.py` |

### 2.2 多用户资源隔离

#### 需求说明

不同用户需要隔离知识库、模型、技能、伙伴和权限边界。

#### 基础要求与业务规则

- admin 和普通用户的 workspace 不同。
- 资源授权必须可审计。
- 不允许把 admin 专属资源误分配给 admin 自己的主 workspace。

#### 验收标准

- 可以按用户查看 grant。
- 可以按用户分配资源。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| multi-user router | `deeptutor/multi_user/router.py` |
| grants | `deeptutor/multi_user/grants.py` |
| identity | `deeptutor/multi_user/identity.py` |
| knowledge access | `deeptutor/multi_user/knowledge_access.py` |
| tool access | `deeptutor/multi_user/tool_access.py` |

### 2.3 移动端与个人资料

#### 需求说明

除了桌面 Web 登录，还要支持移动端 token 和 profile 头像设置。

#### 基础要求与业务规则

- mobile auth 只服务特定 client / purpose。
- 头像和角色更改必须经过校验。

#### 验收标准

- 可以刷新移动端 access token。
- 可以更新 profile avatar。

#### 技术细节与设计代码位置

| 职责 | 代码位置 |
| --- | --- |
| mobile auth router | `deeptutor/api/routers/mobile_auth.py` |
| profile / avatar | `deeptutor/api/routers/auth.py` |
| 前端 multi-user 组件 | `web/features/multi-user/*` |

## 三、多用户与权限模块功能

### 3.1 登录与登出

#### 需求说明

用户要能登录、退出和查看状态。

#### 基础要求与业务规则

- 登录态通过 cookie 或 bearer token 识别。
- 退出要清理 cookie。

#### 验收标准

- status 接口可反映登录状态。

#### 技术细节与设计代码位置

- `deeptutor/api/routers/auth.py`
- `deeptutor/services/auth.py`

### 3.2 资源授权

#### 需求说明

管理员可以把模型、知识库、技能、伙伴和工具分配给用户。

#### 基础要求与业务规则

- 授权结果必须可存储。
- 只允许分配可承载的资源。

#### 验收标准

- `/admin/resources` 可返回可分配清单。
- `/users/{user_id}/grants` 可读写。

#### 技术细节与设计代码位置

- `deeptutor/multi_user/router.py`
- `deeptutor/api/routers/auth.py`
- `web/features/multi-user/api.ts`

### 3.3 资源隔离与审计

#### 需求说明

用户资源必须隔离，管理员操作要可追踪。

#### 基础要求与业务规则

- owner-bound 资源不能被错误分配。
- admin 操作需要写审计日志。

#### 验收标准

- 资源归属和审计记录都能查到。

#### 技术细节与设计代码位置

- `deeptutor/multi_user/audit.py`
- `deeptutor/multi_user/model_access.py`
- `deeptutor/multi_user/paths.py`

## 整体业务流程

```text
用户登录
  ↓
签发 token / cookie
  ↓
进入 request-local current_user
  ↓
解析可见资源与可写资源
  ↓
admin 分配 grants
  ↓
请求在各子系统中按权限落地
```

## 状态模型

- 身份：未登录、已登录、已禁用、管理员、普通用户。
- 授权：未分配、已分配、只读、可写、owner-bound。
- mobile token：有效、过期、刷新中、被拒绝。

## 数据与持久化

- 用户和角色信息由 auth 服务管理。
- grant 数据由 multi_user 持久化。
- 头像与移动端 token 有独立存储和校验逻辑。

## 错误模型

- 登录失败。
- token 无效或过期。
- 权限不足。
- 资源不存在。
- 不可分配资源被误选。

## 与其他模块的接口边界

- 上游：API、Web、CLI、伙伴、技能管理。
- 下游：auth、multi_user、路径服务、资源访问服务。
- 不负责：资源业务本身的生成或执行逻辑。

## 测试策略

- 登录、退出、WebSocket 鉴权和授权分配都需要测试。
- mobile token 的拒绝和刷新路径需要单独回归。
